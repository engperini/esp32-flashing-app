# Improvements backlog

Only current, actionable work belongs here. Remove an item after it is implemented and physically/functionally validated. Each item must describe the current limitation and the expected result; implementation jargon alone is not sufficient.

## Priority 1 — ESP-IDF Component Manager compatibility

- **Support and physically validate external ESP-IDF dependencies exactly as on a PC.** Project files already allow arbitrary text files and the Build already runs the project's normal `idf.py build` inside the ESP-IDF 5.5 environment. Make `main/idf_component.yml` part of the bundled Example project and keep it editable in the Project editor. The app must not implement its own dependency resolver: ESP-IDF Component Manager must read the manifest during CMake, resolve/download Registry or Git dependencies, generate/update `dependencies.lock`, populate `managed_components/`, and then compile/link them normally. Validate this on Android with a small official Espressif Registry component that is actually referenced by the Example firmware, not merely downloaded. Preserve `dependencies.lock` as an ESP-IDF-generated project file and never hand-edit it; treat `managed_components/` as generated dependency cache rather than user source. Acceptance: starting from a project without the dependency cached, Build visibly resolves/downloads it, creates the expected Component Manager outputs, compiles/links the firmware, and the resulting firmware passes the existing native Flash/reset/Serial flow on physical ESP32 hardware. Do not modify the validated ESP32 or ESP32-S3 USB/flash/reset protocols for this work.

## Priority 2 — Generic ESP-IDF targets (Build first, Flash separately)

- [ ] **Discover supported targets from the installed ESP-IDF 5.5 instead of hardcoding two choices.** `SupportedTargets.values` currently lists only `esp32` and `esp32s3`; `ProjectManager.setTarget()`, `needsTargetSwitch()`, and the UI selector depend on it. Read the supported target identifiers from the actual installed ESP-IDF release, validate selections against that list, and show whether each target's toolchain is installed/available. Distinguish ESP-IDF chip targets from board-specific GPIO/USB/reset configurations.
- [ ] **Make target installation lazy and architecture-independent.** `IdfBuildStages` already caches a per-target installation marker and `IdfRuntimePlan.targetInstallCommand()` already delegates installation to `install.sh`, but the latter assumes identifiers begin with `esp32` and `buildPrepared()` requires an installed stage. Remove the prefix assumption, use the ESP-IDF-discovered identifiers, install missing toolchains on demand with progress/cancellation, and reuse completed stages. Verify that the required toolchain binaries exist for the Android Debian ARM64 environment; do not claim all ESP-IDF targets are installable without this check.
- [ ] **Make Doctor architecture-independent.** `IdfBuildExecutor.doctor()` currently contains a two-branch shell `case` for the ESP32 and ESP32-S3 Xtensa compilers. Inspect the toolchain actually configured by ESP-IDF, including RISC-V targets, and report useful errors when a compiler is unavailable.
- [ ] **Keep official target-switch and dependency behavior.** Before Build/Reconfigure, compare `sdkconfig`'s `CONFIG_IDF_TARGET` with the selected target and run `idf.py set-target <target>` only when needed. Preserve incremental builds and automatic `idf.py reconfigure` when `idf_component.yml` changes; preserve project sources and existing toolchains. Verify transitions across at least ESP32, ESP32-S3, and one RISC-V target.
- [ ] **Separate Build support from Flash support.** `FlashPlanLoader.parse()` currently rejects targets outside `SupportedTargets.values`, and `MainActivity.startFlash()` treats every chip other than `esp32` as `esp32s3`. Allow validated firmware artifacts to be built for newly supported targets while disabling native Flash for targets without a verified protocol implementation. Never silently route an unknown chip to the ESP32-S3 ROM flow.
- [ ] **Refactor native Flash into explicit, tested chip strategies.** `EspRomTransport` has chip-dependent SYNC, ROM command formats, Flash parameters (including a fixed 2 MB size), MD5 verification and watchdog reset behavior. `UsbDeviceEngine` has different boot/reset control-line sequences. Introduce chip/board capabilities and ROM transport strategies, detect the connected chip before writing, and enable each new chip only after hardware tests. Keep the already validated ESP32 and ESP32-S3 flash/reset/serial paths unchanged until replacement implementations are proven.
- [ ] **Use a hardware-independent bundled example.** Base new projects on Espressif's ESP-IDF v5.5 `examples/get-started/hello_world`, preserving a small official `esp-lib-utils` API invocation as a Component Manager integration check. Avoid hardcoded PCA9685/I2C GPIO assumptions in the default example. Preserve existing projects because `ProjectManager.ensureExampleProject()` creates files only when absent. Review `sdkconfig.defaults` for chip-specific defaults.
- [ ] **Extend CI and Android acceptance tests.** Test target discovery/validation, ARM64 toolchain installation, Xtensa and RISC-V builds, target switches in both directions, dependency resolution/lockfile generation, cached artifacts, unsupported-Flash rejection, and the existing ESP32/ESP32-S3 hardware Flash/reset/monitor regressions. CI green alone is not proof of Android ARM64 or physical Flash compatibility.

### Proposed official esptool integration — investigation only (do not implement yet)

- [ ] **Investigate why the previous Android USB-to-Termux bridge failed before selecting a new architecture.** Recover the earlier `engperini/esp-idf-android-bridge` experiment, its actual logs/code, and identify whether the failure was USB permission/ownership, Termux execution context, pySerial device visibility, DTR/RTS handling, PRoot networking, process lifecycle, or another demonstrated cause. Do not assume the current app executes through Termux: the current code runs ESP-IDF in an app-managed Debian/PRoot runtime via `ProotLauncher`, while USB access is handled natively through Android `UsbManager` / `UsbDeviceEngine`. Verify whether the bridge can be reached from that specific runtime, including when Android backgrounds the app.
- [ ] **Prototype official esptool over an Android-native USB serial bridge, initially read-only.** Preserve the current physically tested ESP32 and ESP32-S3 Kotlin ROM flashing and reset implementations. Evaluate a localhost RFC2217 bridge (preferred for baud rate and DTR/RTS control), a raw `socket://` bridge (cannot control baud/reset), and/or a custom pySerial transport. Check whether app-managed PRoot and Android can communicate over loopback and whether the Android USB port can be exclusively owned without conflicts with Serial Monitor. First test `esptool` chip identification and `flash-id` only; do not write or erase flash during this proof.
- [ ] **Let the official ESP-IDF/esptool decide chip-specific flash operations after bridge validation.** ESP-IDF generates `flasher_args.json` / flash arguments and invokes esptool for `idf.py flash`. Esptool can auto-detect chips, select chip-specific ROM behavior, and optionally upload its RAM flasher stub. Study esptool's actual version bundled with ESP-IDF 5.5 and pass the generated build arguments without inventing offsets, flash sizes, or chip protocols. Verify ROM vs stub behavior, chip/firmware target mismatch rejection, reset/bootloader line control, verification, reconnect, and cancellation. Do not assume two existing ROM paths cover every chip.
- [ ] **Require a staged migration and physical acceptance tests.** Run the bridge/esptool path alongside, not instead of, the existing proven native flasher. Test ESP32 and ESP32-S3 first, including flash/reset/serial monitoring and screen-off lifecycle, then other chips one by one. Do not switch the default flasher or remove native fallback until physical tests demonstrate equal or better reliability and safe recovery.
- **Official references:** [Espressif esptool remote serial ports / RFC2217](https://docs.espressif.com/projects/esptool/en/release-v4/esp32/esptool/remote-serial-ports.html), [esptool chip detection](https://docs.espressif.com/projects/esptool/en/release-v4/esp32/esptool/basic-options.html), [esptool ROM vs stub protocol](https://docs.espressif.com/projects/esptool/en/release-v4/esp32/advanced-topics/serial-protocol.html), [ESP-IDF flashing](https://docs.espressif.com/projects/esptool/en/release-v4/esp32/esptool/flashing-firmware.html).

## ESP-IDF setup and build

- **Cancel ESP-IDF Configure safely.** The Build operation already has a validated Cancel path, but Configure/Setup does not expose equivalent cancellation. Add cancellation for an active provisioning/download/install session without deleting stages that were already completed successfully. Starting Configure again must resume from the first incomplete stage.
- **Reduce Build startup overhead.** Every Build currently enters the ESP-IDF environment by sourcing `/opt/esp/idf/export.sh` before running `idf.py build`. Measure how much time this adds on Android and, only if material, replace it with a cached/precomputed environment that preserves the exact ESP-IDF 5.5 tool paths and Python environment.

## Build & Flash workflow

- **Make the Build & Flash button complete both operations automatically.** Today `ACTION_BUILD_FLASH` performs the Build and validates/saves its flash images, but then stops with “tap Flash to continue safely”; the user must press Flash separately. After a successful Build, the requested combined operation must automatically start the same already-validated native Flash flow. A failed or cancelled Build must never start Flash. Do not change the separately validated ESP32 and ESP32-S3 flash/reset sequences while implementing this.

## Project workflow

- **Support multiple projects instead of the single fixed Example project.** `ProjectManager` currently points permanently to `filesDir/projects/example`. Add create/select/rename/delete project operations, with each project keeping its own files and selected ESP target.
- **Complete file management in the Project explorer.** Creating files and folders is implemented; add rename and delete for project files/folders with the same path-containment protection already used by `safeFile()`.
- **Add project import/export.** Define a portable ESP-IDF project package that preserves source files and app project metadata, while excluding generated Build output and internal cached flash artifacts.

## Flash artifact safety and diagnostics

- **Guarantee that the previous validated firmware remains available if artifact promotion is interrupted.** After every successful Build, `FlashPlanLoader.promoteLastGood()` copies the required ESP-IDF flash files into `.last-good-flash.tmp` and validates the complete temporary set. It then deletes the previous `.last-good-flash` before renaming the temporary directory. If the process/device dies in that small delete→rename window, the previously validated firmware set can be lost. Replace it with a swap/backup strategy that always leaves either the old complete set or the new complete set recoverable. This cache exists so the Flash button uses a complete firmware set from a successful Build rather than partially generated files from a failed/interrupted Build.
- **Make Flash preflight errors identify the bad artifact.** `FlashPlanLoader` already validates `flasher_args.json`, target, image paths and file existence. Improve user-facing errors so a missing/corrupt cached image tells the user which file/set is invalid and whether rebuilding is the recovery action, instead of falling back to a generic Flash failure.

## Application and Serial Monitor state

- **Track Serial Monitor activity independently from the global operation status.** `AppState.operation` is shared by Build, Setup, Flash and Serial Monitor, while `UsbDeviceEngine.startMonitor()` writes `MONITORING` whenever serial data arrives. This allows unrelated operations and incoming serial data to overwrite each other’s displayed state. Keep an independent monitor-running/serial status so the UI can truthfully show “Serial active” while Build/Setup/other operations have their own status.
